# 검색 성능·품질 실험

현재 검색은 MySQL `LIKE '%키워드%'`로 구현되어 있다. 이 방식의 한계를 재현 가능한
숫자로 만들기 위한 도구 모음이다.

## 왜 이 구조인가

측정하려는 것이 두 가지인데, 둘은 방법이 다르다.

| 축 | 무엇을 재나 | 합성 가능? | 도구 |
| --- | --- | --- | --- |
| **성능** | p95, 스캔 행 수, 커넥션 대기 | 가능 | 시드 데이터 + k6 + 그라파나 |
| **품질** | 무결과, 오타·동의어 처리 | 불가능 | 골든셋 + 평가 러너 |

성능은 부하와 데이터 규모를 합성하면 되므로 사용자가 필요 없다. 문제는 품질이다.
무결과율 같은 지표는 실사용 트래픽이 있어야 의미가 있는데, 사람을 모아도 문제가
완전히 풀리지 않는다. **검색어를 치는 사람이 데이터를 아는 사람**이라, 나도 모르게
DB에 있는 이름을 정확히 치기 때문이다. 표본이 작은 것보다 이 선택 편향이 더 크다.

그래서 품질 축은 관측 대신 **통제된 실험**으로 바꾼다. 사람이 검색어를 떠올리는 게
아니라, DB에 있는 스팟에서 검색어를 기계적으로 파생시킨다. 파생 규칙이 곧 실험
조건이고 정답이 이미 정해져 있으니 적중률을 셀 수 있다. 정보검색(IR) 분야에서
test collection이라고 부르는 평가 방식이다.

## 준비물

- Node.js 18+ (외부 패키지 없음)
- k6 (부하 테스트용)
- 실행 중인 앱과 MySQL

## 실행 순서

### 1. 골든셋 생성 (오프라인, DB 불필요)

```bash
node search-eval/generate-goldenset.js
```

`src/main/resources/spot_data.sql`의 실제 스팟 135건에서 검색어 약 860건을 파생한다.

| 유형 | 예시 | 사전 예상 |
| --- | --- | --- |
| `exact` | 갈산공원 | 적중 (기준선) |
| `prefix` | 갈산공 | 적중 |
| `substring` | 산공원 | 적중 |
| `spacing_removed` | 강남 마이스 관광특구 → 강남마이스관광특구 | 실패 |
| `spacing_added` | 갈산공원 → 갈 산공원 | 실패 |
| `typo_adjacent` | 강남 마이스 → 강남 나이스 (두벌식 인접키) | 실패 |
| `typo_jongseong` | 갈산공원 → 가산공원 (종성 누락) | 실패 |
| `synonym` | 해수욕장 → 바다 | 실패 |
| `natural` | NIGHT_VIEW → 야경 예쁜 곳 | 실패 |

사전 예상은 **측정 전에** 골든셋 안에 박아둔다. 결과를 보고 기준을 정한 게 아니라는
것을 보이기 위해서다. `exact`가 100%가 안 나오면 실험 자체가 잘못된 것이므로
기준선 역할도 한다.

### 2. 품질 평가

```bash
./gradlew bootRun                                          # 앱 먼저
node search-eval/evaluate-quality.js --label "필러 없음"
```

`search-eval/out/quality-report-*.md`에 리포트가 떨어진다. 지표 네 가지:

- **무결과율** — 결과 0건. 문자열 매칭 자체가 실패.
- **적중률@k** — 정답이 상위 k건 안에 있는 비율. 사용자가 실제로 보는 것.
- **Recall@k** — 정답 집합 중 몇 %를 담았는지. 동의어/자연어처럼 정답이 여러 건일 때 의미 있음.
- **매칭O·순위밖** — 결과는 나왔는데 정답이 밀려남. **매칭이 아니라 랭킹의 실패**다.
  현재 검색은 `createdAt DESC` 정렬이라 관련도 개념이 없어서, 데이터가 늘수록 이 값이 커진다.
  무결과율만 보면 이 실패는 안 보인다.

### 3. 시드 데이터 적재 (성능 축)

```bash
node search-eval/generate-seed.js --count 100000
mysql -u root -p --default-character-set=utf8mb4 picngo -e "source search-eval/out/seed/seed-001.sql"
```

적재에 `< 파일` 리다이렉션 대신 mysql 클라이언트의 `source`를 쓰는 이유가 두 가지 있다.

1. **PowerShell은 `<` 입력 리다이렉션을 지원하지 않는다**(예약 연산자라 파서 오류가 난다).
   `source`는 PowerShell·cmd·Git Bash 어디서든 같은 형태로 동작한다.
2. 파일을 mysql이 직접 읽으므로 셸 파이프를 거치며 인코딩이 다시 바뀌지 않는다.

`--default-character-set=utf8mb4`도 빼면 안 된다. Windows의 mysql 클라이언트는
콘솔 코드페이지(cp949)를 따라가는 경우가 있어서, 이걸 빼면 한글 이름과 overview가
깨진 채로 들어간다. 깨진 데이터로는 검색 실험이 성립하지 않는다.

- 필러는 `id 1000000`부터. 실제 스팟 135건은 건드리지 않는다.
- `overview`를 200~800자로 채운다. 검색 쿼리가 이 TEXT 컬럼까지 LIKE로 훑기 때문에
  비워두면 실제 스캔 비용을 크게 과소평가하게 된다.
- 되돌리기: `search-eval/out/seed/cleanup.sql`

같은 `--seed` 값이면 항상 같은 데이터가 나온다.

### 4. 부하 테스트

```bash
k6 run -e LABEL=10만건 -e SEARCH_VUS=30 -e MAP_VUS=20 load-test/search-load.js
```

검색어는 골든셋에서 가져온다(387건). 손으로 고른 몇 개를 반복하면 그것만 버퍼풀에
올라가서 실제보다 빠르게 측정되기 때문이다.

지표는 k6 요약이 아니라 **그라파나에서** 본다. k6는 부하를 만드는 역할이고,
관측은 앱·MySQL 지표로 한다. k6 요약은 클라이언트 관점 교차검증용.

### 5. 대시보드

`monitoring/grafana/search-performance-dashboard.json`을 Grafana에서 Import.

### 6. 데이터 규모를 바꿔가며 3~5 반복

| 필러 | 검색 p95 | 스캔 행/초 | 선택도 | 버퍼풀 히트율 | 무결과율 |
| --- | --- | --- | --- | --- | --- |
| 0 | | | | | |
| 1만 | | | | | |
| 10만 | | | | | |
| 100만 | | | | | |

**SLO는 측정 전에 정한다.** 검색 p95 < 200ms, p99 < 500ms @ 동시 100.
재고 나서 기준을 맞추면 결론에 맞춰 숫자를 고른 게 된다.

## LIKE vs FULLTEXT 대조 실험

성능이 나쁘다는 것만으로는 "MySQL의 한계"라고 말할 수 없다. 지금 쿼리가 선행
와일드카드라 인덱스를 못 타는 것이지, MySQL이 못 하는 게 아니기 때문이다.
MySQL 안에서 해결 가능한 수단(FULLTEXT + ngram)을 먼저 소진해야 그 다음 주장이 선다.

두 방식은 `picngo.search.engine` 설정 하나로 갈린다. 엔드포인트·골든셋·부하 스크립트를
그대로 두고 설정만 바꿔 재측정하므로, 차이를 인덱스 방식으로만 귀속시킬 수 있다.

```bash
# 1) 인덱스 생성 (1회)
mysql -u root -p --default-character-set=utf8mb4 picngo -e "source docs/search-fulltext-index-migration.sql"
```

```bash
# 2) FULLTEXT로 기동
SEARCH_ENGINE=FULLTEXT ./gradlew bootRun
```

```bash
# 3) 같은 골든셋으로 품질 재측정
node search-eval/evaluate-quality.js --label "FULLTEXT / 10만건"
```

```bash
# 4) 같은 조건으로 부하 재측정
k6 run -e LABEL=fulltext-10만 -e SEARCH_VUS=30 -e MAP_VUS=20 load-test/search-load.js
```

PowerShell이면 2번은 `$env:SEARCH_ENGINE="FULLTEXT"; ./gradlew bootRun`.

모든 지표에 `engine` 태그가 붙으므로 그라파나 대시보드의 **검색 엔진** 변수로 두 측정을
겹쳐 볼 수 있다. **지도 검색이 대조군이다** — 지도 쿼리는 엔진 설정과 무관하므로 두
측정에서 값이 같아야 한다. 지도까지 달라졌다면 차이의 원인이 인덱스가 아니라 측정
환경(캐시 상태, 백그라운드 부하 등)에 있다는 신호다.

### 결과를 채울 표

| 지표 | LIKE | FULLTEXT | 해석 |
| --- | --- | --- | --- |
| 검색 p95 | | | 성능이 MySQL 안에서 해결되는가 |
| EXPLAIN type / key | ALL / NULL | | 인덱스를 실제로 타는가 |
| 인덱스 크기 (MB) | | | 속도의 대가로 치른 저장 비용 |
| 정확 일치 적중률 | | | 기준선. 둘 다 100%에 가까워야 정상 |
| 띄어쓰기 적중률 | | | ngram이 잡아줄 가능성이 높은 구간 |
| **오타 적중률** | 0% | | **인덱스로 해결 안 될 것으로 예상** |
| **동의어·자연어 적중률** | 0% | | **인덱스로 해결 안 될 것으로 예상** |

굵게 표시한 두 줄이 벡터 검색의 근거가 될 자리다. FULLTEXT로도 0%면 "인덱스로는
해결되지 않는 종류의 문제"라는 것이 측정으로 확인된다. 반대로 성능과 띄어쓰기가
FULLTEXT로 해결되면, 그건 실패가 아니라 **더 싼 방법으로 풀 수 있는 문제를
비싼 방법으로 풀지 않았다는 증거**다.

### 주의: 매칭 의미를 맞춰야 비교가 성립한다

ngram 파서는 '한라산'을 '한라', '라산' 두 토큰으로 쪼갠다. 따옴표 없이 BOOLEAN MODE로
넘기면 이 토큰들이 OR로 묶여 '한라'만 든 스팟까지 걸린다. 그래서 검색어를 큰따옴표로
감싸 **구문(phrase) 검색**으로 만든다(`FullTextKeyword`). 그래야 `LIKE '%한라산%'`과
같은 의미가 되고, 두 방식의 결과 집합을 비교할 수 있다.

정렬도 양쪽 다 `created_at DESC`로 맞췄다. FULLTEXT의 관련도 정렬로 바꾸면 인덱스와
랭킹 두 가지가 동시에 바뀌어 무엇 때문에 좋아졌는지 말할 수 없게 된다. 관련도 정렬은
그 다음 단계의 별도 변수로 다룬다.

## 검색 품질 개선 — 단계적 폴백

측정 결과 실패 유형이 세 덩어리로 갈렸고, 필요한 기술이 각각 다르다.

| 덩어리 | 골든셋 건수 | 필요한 기술 | MySQL 안에서 |
| --- | ---: | --- | --- |
| 띄어쓰기 | 160 | 공백 지운 색인 | 가능 |
| 오타 | 260 | 자모 단위 유사도 | 가능 |
| 의미(동의어·자연어) | 37 | 임베딩 | 불가 |

그래서 검색을 한 번에 끝내지 않고 **앞 단계가 0건일 때만 다음으로 물러나는 구조**로 바꾼다.
층을 하나씩 얹으면서 골든셋으로 유형별 개선폭을 따로 잴 수 있다.

```
1) 기본 검색 (LIKE 또는 FULLTEXT)   → 결과 있으면 끝
2) 띄어쓰기·문장부호 무시 재시도      → 있으면 끝
3) 유사도 검색 (오타 흡수)           → 있으면 끝
4) (검증 중) 의미 검색
```

### 4층: 의미 검색 — 오프라인 검증 먼저

**저장소를 고르기 전에 효과부터 잰다.** pgvector냐 Elasticsearch냐는 그다음 문제다.
여기서 효과가 없으면 무엇을 골라도 소용없고, 있으면 그 수치가 선택의 근거가 된다.

DB도 서버도 필요 없다. 스팟과 검색어를 벡터로 바꿔 유사도만 계산한다.

```bash
node search-eval/embed-corpus.js
```

```bash
node search-eval/evaluate-vector.js --label "임베딩 / 이름+주소"
```

PowerShell에서 키 넣기: `$env:OPENAI_API_KEY="sk-..."`

임베딩은 한 번 만들어 `out/embeddings.json`에 캐시한다. 평가는 몇 번이든 공짜로 다시 돌린다.
골든셋을 다시 만들었다면 임베딩도 다시 만들어야 하며, 개수가 안 맞으면 평가가 막아준다.

#### 무엇을 임베딩하는지가 결과를 좌우한다

실제 스팟 130건에는 **설명문(overview)이 없다.** 이름과 주소뿐이다.
그래서 '야경 예쁜 곳'으로 '남산 팔각정'을 찾으려면 모델이 이름만 보고 그곳이
야경 명소임을 알아야 한다. 모델의 세계 지식에 기대는 셈이다.

결과가 나쁘면 **"벡터 검색이 안 된다"가 아니라 "설명 텍스트가 없어서 안 된다"** 일 수 있다.
두 결론은 해결책이 완전히 다르다(기술 교체 vs 데이터 확보). 구분하려면 설명문을 붙여 한 번 더 잰다.

```bash
node search-eval/embed-corpus.js --with-overview
```

**카테고리는 임베딩에 넣지 않는다.** 자연어 검색어의 정답 판정 기준이 바로 그 카테고리라,
입력에 넣으면 정답을 알려주고 맞히라는 셈이 되어 측정이 무의미해진다.

#### 비교할 때 주의

벡터 검색은 아무리 관련이 없어도 **항상 상위 k건을 돌려준다.** 무결과율이 0%로 고정되므로
문자열 검색의 무결과율과 비교하면 안 된다. **적중률·Recall·MRR로만 비교할 것.**

특히 동의어·자연어는 정답이 여러 건이라 **Recall이 핵심**이다. 적중률이 높아도 Recall이
낮으면 "여러 개 중 하나만 어쩌다 걸린 것"이다.

### 2층: 띄어쓰기 무시

```bash
mysql -u root -p --default-character-set=utf8mb4 picngo -e "source docs/search-normalized-column-migration.sql"
```

```bash
SEARCH_ENGINE=FULLTEXT SEARCH_NORMALIZE_FALLBACK=true ./gradlew bootRun
```

PowerShell이면 `$env:SEARCH_ENGINE="FULLTEXT"; $env:SEARCH_NORMALIZE_FALLBACK="true"; ./gradlew bootRun`

```bash
node search-eval/evaluate-quality.js --label "FULLTEXT + 띄어쓰기 폴백"
```

`spacing_removed`(30건)와 `spacing_added`(130건)의 적중률이 얼마나 오르는지가 이 층의 성적이다.
직전 측정값은 각각 3.3%, 7.7%였다.

### 3층: 유사도 검색 (오타 흡수)

**추가 마이그레이션이 없다.** 2층과 같은 색인(`ft_spot_search_norm`)을 쓰되 조회 방식만 바꾼다.

|  | 검색식 | 의미 |
| --- | --- | --- |
| 1·2층 | `"갈산공원"` (따옴표 O) | 조각들이 그 순서 그대로 있어야 매칭 |
| 3층 | `갈산공원` (따옴표 X) | 조각이 몇 개 겹치는지로 점수를 매김 |

```
검색어 갈산공줜 -> 두 글자 조각: 갈산 · 산공 · 공줜
저장값 갈산공원 -> 두 글자 조각: 갈산 · 산공 · 공원
                                 3개 중 2개 일치
```

오타가 난 검색어는 원본과 정확히 일치할 수 없어 구문 검색으로는 영원히 못 찾는다.
겹침을 점수로 환산하면 흡수할 수 있다.

이 단계만 정렬이 최신순이 아니라 **관련도순**이다. 조각 하나만 겹쳐도 후보에 들어오므로
최신순으로 두면 엉뚱한 스팟이 위로 올라와 쓸모가 없어진다.

```bash
SEARCH_ENGINE=FULLTEXT SEARCH_NORMALIZE_FALLBACK=true SEARCH_SIMILAR_FALLBACK=true ./gradlew bootRun
```

```bash
node search-eval/evaluate-quality.js --label "FULLTEXT + 띄어쓰기 + 유사도"
```

**볼 것이 두 가지다.** 오타 유형(`typo_adjacent`, `typo_jongseong` 각 130건)의 적중률이
오르는지, 그리고 **MRR이 얼마나 되는지**. 적중률만 높고 MRR이 낮다면 정답이 20위 안에는
들었지만 한참 뒤에 있다는 뜻이라, 사용자에게는 못 찾은 것과 큰 차이가 없다.

짧은 이름은 이 방식으로 잡히지 않을 수 있다. '강남'의 오타 '강넘'은 두 글자 조각이
`강남` 하나뿐이라 겹치는 게 없다. 그런 경우가 많으면 자모 단위 색인이 다음 후보가 된다.

### 층이 실제로 쓰이는지 확인

층을 추가할 때마다 **그 층이 실제로 결과를 내는지** 봐야 한다.
안 쓰이는 층은 비용만 쓰고 있는 것이다.

```promql
sum by (stage) (rate(spot_search_stage_total[5m]))
  / scalar(sum(rate(spot_search_stage_total[5m])))
```

- `primary` — 기본 검색이 바로 찾음
- `normalized` — 띄어쓰기를 무시하고 재시도해서 찾음
- `none` — 끝내 못 찾음

**`none`이 줄어드는 것이 폴백을 추가한 목적이고, `normalized`가 그 몫이다.**
대시보드에도 같은 패널이 있다.

폴백은 앞 단계가 0건일 때만 도는 추가 쿼리라, 결과가 나오는 검색의 비용은 그대로다.
성능에 영향이 없다는 것도 k6로 확인해두면 좋다.

## 이 수치로 주장할 수 있는 것과 없는 것

**주장할 수 있는 것**

- 데이터 규모별 응답시간 곡선과 SLO가 깨지는 지점
- 지연이 검색 SQL에서 오는지 N+1에서 오는지의 비중
- 오타/띄어쓰기/동의어/자연어 각 유형의 적중률

**주장할 수 없는 것**

- 실사용자의 검색어 분포. 골든셋은 데이터에서 파생한 것이지 검색 로그가 아니다.
- 변형 규칙(어떤 오타를 낼지, 어떤 동의어를 쓸지)은 결국 사람이 골랐다. 이 선택 자체가 편향이다.
- `natural` 유형의 정답 집합은 `spot_categories` 태깅에 의존하는데, 장면형 카테고리는
  키워드 추출 기반이라 오탐이 있다(`SpotCategoryTagger` 주석 참고).

한계는 리포트에도 자동으로 같이 출력된다. 지우지 말 것 — 한계를 밝힌 측정이
한계를 숨긴 측정보다 신뢰도가 높다.

## 결과 해석 시 주의

성능 문제가 나오더라도 그것이 곧 "MySQL의 한계"는 아니다. 지금 쿼리는 선행
와일드카드라 인덱스를 못 타는 형태이고, MySQL 8에는 아직 쓰지 않은 수단이 있다:

- **FULLTEXT + ngram parser** — 한국어 형태소 대응, `MATCH ... AGAINST`
- **SPATIAL 인덱스** — `POINT` + R-Tree로 지도 bounds 이중 range 해소

이것들을 적용하고도 SLO를 못 지킬 때 비로소 스토리지 교체를 말할 수 있다.
반대로 오타·동의어·자연어는 인덱스로 해결되지 않는 종류의 문제라, 그쪽은 처음부터
다른 접근(임베딩 기반 검색)이 필요하다. 두 축을 섞지 말 것.
